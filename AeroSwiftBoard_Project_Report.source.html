ABSTRACT

Airline boarding can become difficult to coordinate when passengers gather at a gate after an announcement and staff must call them in an orderly sequence. This project presents AeroSwiftBoard, a small web application prototype that demonstrates a digital boarding queue and configurable priority ordering. The interface is implemented with plain HTML, CSS, and JavaScript; the backend uses Java and Spring Boot REST APIs.

At application startup, passenger records are read from a classpath CSV file into an in-memory singleton state. The user interface requests the next five passengers and displays their names, zones, veteran status, and a senior-citizen indicator derived from age 58 or above. A gate operator can select a displayed passenger to record boarding. The backend removes that passenger from the current queue and reports the remaining passenger count. The interface also offers senior-citizen and veteran preference selections. These preferences are stored in memory and determine which comparator orders the next list: default business-class and zone order, senior-citizen-first order, or senior-citizen-and-veteran order.

The project uses Spring MVC controllers, service classes, Java collections, comparator-based sorting, and JUnit/Spring MockMvc tests. Verification covers CSV loading, comparator selection, queue retrieval, input validation, and passenger removal. The prototype does not integrate with airline systems, persist boarding state, authenticate users, or measure operational boarding-time improvement. It provides a foundation for discussing how a clear, API-driven gate display could support a more organized boarding workflow.

Keywords: flight boarding, Java, Spring Boot, REST API, comparator, passenger queue, web application.

CHAPTER 1 — INTRODUCTION

1.1 Background

Boarding is the final passenger-facing process before an aircraft departs. At a gate, staff must communicate who may board, keep the line moving, and respond to passengers who need assistance. A gate announcement can prompt many passengers to approach at nearly the same time. If the sequence is not visible or is difficult to follow, passengers may be uncertain about when they should join the line. A display that makes the next group and the ordering rule easy to understand can support communication between the gate team and passengers.

Boarding order is also an operational problem. Airlines may organize boarding by cabin, zones, seating location, loyalty status, accessibility needs, or other policies. These policies are not interchangeable: the most appropriate sequence depends on the airline's operational goals, aircraft layout, passenger mix, and service rules. This project does not attempt to optimize a real airline schedule. Instead, it implements a small, explicit priority policy that can be changed through the interface and evaluated as a programming exercise.

AeroSwiftBoard is a single-page gate display connected to a Java backend. On initial load, the browser requests a list of five passengers. The backend returns passenger records ordered using the active comparator and also reports the size of the full remaining queue. A user can select a passenger to board; the backend removes that passenger from the in-memory state, and the browser refreshes the list. Optional senior-citizen and veteran selections change the sorting comparator. The front end is built with native browser technologies instead of a framework so the request/response behavior is visible to a beginner developer.

1.2 Problem Statement

At a busy boarding gate, passengers may gather immediately after an announcement and have limited visibility into the intended boarding sequence. A static or verbal process can make it harder to communicate the next passengers and to reflect priority choices consistently. The project addresses this learning-scale problem by providing a web screen that displays the next five passengers in a deterministic priority order, accepts boarding actions, and refreshes the queue through REST APIs. It does not claim that a digital display alone resolves airport crowding or improves measured boarding time.

1.3 Aim and Objectives

Aim: To design and implement a beginner-friendly web prototype for displaying and managing a prioritized list of passengers at a flight boarding gate.

  1. Build a single-screen, responsive boarding display using plain HTML, CSS, and JavaScript.
  2. Implement a Java/Spring Boot backend with APIs for listing passengers, recording boarding, and saving priority preferences.
  3. Load passenger sample records from a CSV resource at startup and maintain the active queue in a singleton application service.
  4. Implement comparator-based ordering for default, senior-citizen, and veteran-aware priority modes.
  5. Display useful queue details while representing senior-citizen status as Yes/No for passengers aged 58 or above.
  6. Validate the core backend behavior with automated tests and document known limitations and future extensions.

1.4 Scope

The scope includes local application startup, CSV parsing, in-memory passenger state, a static single-page interface served by Spring Boot, queue retrieval with a configurable positive limit, passenger boarding by boarding-pass number, and an API that stores two Boolean preferences. The default order is Business_Class, Zone C, Zone B, and Zone A. When senior-citizen preference is active, passengers aged 58 or above are ranked first. When veteran preference is active, the combined comparator ranks seniors first, then veterans, followed by the default cabin/zone order.

The project uses a sample CSV and illustrative flight details in the UI. It is not connected to a check-in system, airline reservation database, flight schedule, gate display network, identity service, or boarding-pass scanner. The queue resets from the CSV when the application restarts. The UI preference state also resets to false/false at startup. The browser does not sign in an operator, and the backend has no authorization, audit trail, persistent database, distributed state, or production deployment configuration.

1.5 Project Significance

The project demonstrates an end-to-end software path: records are read from a file, represented as Java objects, ordered by explicit comparison rules, exposed as JSON through HTTP, and presented in a browser. It provides a concrete example for studying API boundaries, data structures, state management, user feedback, input validation, and automated tests. Its value is educational and demonstrative rather than operational.

CHAPTER 2 — LITERATURE SURVEY

2.1 Introduction

Aircraft boarding has been studied as a problem involving passenger sequencing, seat location, aisle movement, carry-on luggage, and conflicts among passengers entering the same row. Research shows that a boarding rule can affect time and congestion, but a rule that performs well in one model or operating context is not automatically best for every airline. This chapter reviews relevant studies and uses them as context for the limited policy implemented in AeroSwiftBoard. The review does not treat the prototype's comparator policy as a proven optimization.

2.3 Synthesis and Relevance to AeroSwiftBoard

The studies collectively indicate that boarding order is only one part of a larger process. Aircraft configuration, passenger behavior, overhead-bin use, seat assignments, and group travel affect actual boarding time. AeroSwiftBoard therefore treats its ordering rules as configurable demonstration logic rather than an empirically optimal boarding policy. The application makes the policy observable and testable: the active preference determines a comparator, the comparator produces an ordered view, and the UI presents the first five entries.

The gap addressed by this project is not a lack of boarding algorithms. Rather, it is the educational demonstration of a small, understandable software implementation that connects a user-visible boarding sequence to an API and explicit ordering rules. The project does not reproduce the passenger behavior models in academic studies and does not compare boarding times under controlled conditions.

2.4 Limitations of the Review

The review is intentionally focused on selected boarding-order and boarding-time studies. It is not a systematic review of airline operations research, accessibility policy, airport crowd management, or all possible boarding algorithms. The cited works support the motivation for treating boarding sequence as a meaningful design concern; they do not validate the application as a real operational system.

3.6 Comparator Rules

All comparator policies are ascending by priority rank: a lower rank appears earlier in the sorted output. The default comparator ranks Business_Class first, then Zone C, Zone B, and Zone A. Unrecognized or missing zones are assigned a fallback rank after the recognized zones. The senior-citizen comparator places passengers aged 58 or above before other passengers and then delegates ties to the default comparator. The combined comparator first ranks seniors, then veterans, then delegates remaining ties to the default comparator.

3.7 Queue Retrieval and Boarding Algorithm

  1. The browser issues a GET request with a positive limit (the page uses five).
  2. The controller rejects a limit below one, then calls the boarding service.
  3. The service reads the current selection and obtains the matching comparator.
  4. The service sorts a stream of the current list, limits the result, and builds a response containing those passengers and the total queue count.
  5. When a board button is selected, the browser sends a POST request with that passenger's boarding-pass number.
  6. The state service creates a mutable copy, removes the matching record, and publishes a new immutable snapshot.
  7. The browser refreshes the queue and displays the updated count and status message.

Board:   validate boarding-pass number -> remove from copied list -> replace state -> refresh UI

4.3 Priority Comparator Implementation

The default comparator converts the zone into a numeric rank. Senior-aware comparators perform Boolean comparisons in descending priority order and use the default comparator to break ties. Keeping these policies as separate classes makes the business rule readable and testable without embedding condition chains in the controller.

private int priorityRank(Passenger passenger) {
    String zone = passenger.getZone();
    if (zone == null) {
        return 4;
    }
    return switch (zone.trim().toUpperCase()) {
        case "BUSINESS_CLASS" -> 0;
        case "C" -> 1;
        case "B" -> 2;
        case "A" -> 3;
        default -> 4;
    };
}

For the senior criterion, the comparator compares the predicates age >= 58 and then delegates when both passengers fall in the same group. The combined comparator applies a veteran comparison only after senior status is tied. This means a senior non-veteran is ordered ahead of a non-senior veteran in combined mode, as verified by the comparator test.

4.4 Queue Service and State Updates

PassengerBoardingService reads the immutable passenger snapshot, chooses a comparator from the shared preference state, sorts the list, takes at most the requested limit, and returns a record containing both the selected passengers and total count. Boarding is separate: the board API removes a single record, and the UI subsequently requests the updated list.

PassengerState replaces the list with a new immutable snapshot after a successful removal. The collection size is logged after changes. Priority updates are likewise held by a Spring singleton and logged only when a value changes. These choices make the state behavior easy to observe during a local demonstration; neither service saves data across restarts.

5.3 Results and Interpretation

The implemented backend can load the sample passenger set, keep it in memory, return a prioritized prefix, update its priority mode, and remove a selected passenger. The user interface consumes the same APIs and refreshes its visible list after state changes. Comparator behavior is deterministic for the defined rules. The tests confirm the principal data and API flows under local test conditions.

These results demonstrate functional correctness for a prototype and do not establish that passengers will board faster or experience less crowding. Such conclusions would require a controlled field study, operational data, participant feedback, and comparison against a defined baseline. The application also does not model aircraft aisle conflicts, seat positions, carry-on luggage, family groups, accessibility constraints, or gate-agent workload.

5.4 Complexity Analysis

Let n be the number of passengers in the active in-memory list and k be the requested display limit. The analysis below describes asymptotic cost in the current implementation; it is not a benchmark.

OperationTime complexityAdditional spaceExplanation
CSV loadingO(n)O(n)Each row is read and converted once; all passengers are retained.
One comparator invocationO(1)O(1)Uses a small fixed number of field comparisons.
Queue retrievalO(n log n)O(n)The full stream is sorted before limiting to k records.
Passenger removalO(n)O(n)The current list is copied and searched; a new immutable list is stored.
Priority updateO(1)O(1)Replaces an immutable selection record.

For the current dataset of 200 passengers, this simple in-memory approach is appropriate for a classroom demonstration. For a substantially larger dataset or many concurrent users, a database-backed query with indexed attributes and transaction-safe boarding would be more suitable. A partial selection algorithm could reduce the cost of returning a small prefix, but it would add complexity and should be justified by measured scale.

5.5 Limitations and Risks

  • In-memory data: boarded passengers and preferences are lost when the process restarts.
  • Single process: multiple application instances would not share queue state.
  • Policy simplification: comparators encode a small fixed policy and do not represent airline-specific rules.
  • Sample data: passenger records are illustrative; this application should not be given real personal or travel data without appropriate controls.
  • CSV format: the current parser supports the simple sample format, not all CSV quoting and escaping rules.
  • No authentication: any client able to reach the local endpoints could change preferences or board a passenger.
  • No measured outcomes: there is no evidence of improved boarding time, reduced waiting, or passenger satisfaction.

CHAPTER 6 — CONCLUSION AND FUTURE WORK

6.1 Conclusion

AeroSwiftBoard implements a small end-to-end boarding-gate demonstration using Java, Spring Boot, and plain browser technologies. It loads a sample passenger list from CSV, stores the current list and preference state in Spring singleton services, applies explicit comparator policies, exposes REST APIs, and renders the next five passengers in a responsive single-page interface. The application can record the boarding of a selected passenger and refresh the displayed queue.

The project meets its learning objectives by connecting data structures, comparator logic, API design, client-side interaction, and automated testing. The use of an immutable passenger-list snapshot and separate comparator classes keeps state changes and priority rules understandable. The automated test run passed 13 tests covering the key backend behaviors.

The system remains a prototype. Its behavior is limited to a local process and sample data, and it has no persistence, user authentication, operational airline integration, or measured passenger outcome. It should not be deployed as a real airport boarding tool without a substantially broader design, security review, operational validation, and airline approval.

6.2 Future Enhancements

  1. Persistent storage: Add a relational database, transactions, and a durable boarding audit history.
  2. Identity and authorization: Authenticate gate staff and restrict boarding and preference changes to authorized roles.
  3. Operational integration: Integrate through documented airline APIs for flight, passenger, seat, and boarding-pass data, with explicit failure handling.
  4. Policy configuration: Define airline-approved boarding groups and priority rules as validated configuration instead of hard-coded comparators.
  5. Accessibility and resilience: Conduct accessibility testing, provide localized and high-contrast modes, and ensure the screen remains usable when network calls fail.
  6. Queue concurrency: Add idempotent board requests, database locking or equivalent concurrency control, and conflict responses for simultaneous agents.
  7. Observability: Use structured logs and metrics while minimizing passenger information in logs.
  8. Evaluation: Conduct a user study or simulation using an approved, anonymized dataset and compare clearly defined boarding scenarios.

6.3 Final Note

The project's strongest outcome is a transparent demonstration of how a small web interface can call backend APIs and reflect an explicit ordering policy. Future work should prioritize correctness, privacy, accessibility, and operational safety before attempting real-world deployment.
